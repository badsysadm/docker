# ADR: профиль сборки pciutils

## Статус
Принято для проверки сборкой.

## Контекст
Утилитам PCI требуется локальная база идентификаторов устройств
и доступ к конфигурационному пространству PCI через Linux.

## Решение
- Использовать официальный релизный архив pciutils.
- Поставлять `lspci`, `setpci`, `pcilmr` и `update-pciids`
  вместе с базой `pci.ids.gz`.
- Встраивать `libpci` в исполняемые файлы, без общей
  runtime-библиотеки `libpci.so`.
- Оставить поддержку разрешения идентификаторов PCI через DNS.
- Сохранять поддержку сжатой базы `pci.ids.gz` через zlib.
- Сохранять определение модулей ядра через libkmod и разрешение
  названий оборудования через udev HWDB.
- Для статической линковки `pciutils` формировать собственный
  `libkmod.a` из внутренних архивов `libkmod-internal.a` и `libshared.a`
  в `02_dep.Dockerfile` проекта `pciutils`.
- Изолировать конфликтующие глобальные символы в локальном `libkmod.a`,
  чтобы обеспечить совместную линковку с `libudev.a`.
- Не изменять профиль сборки `kmod`: его артефакты и сборка остаются
  независимыми от особенностей статической линковки `pciutils`.

## Последствия
- Имена устройств доступны из поставляемой базы `pci.ids.gz`
  даже без сети; `lspci -q` может использовать DNS.
- `lspci` использует libkmod для подбора модулей и udev HWDB
  как дополнительный источник имён оборудования.
- Статическая интеграция с libkmod обслуживается внутри сборки
  `pciutils` и не требует отдельного `libkmod.a` в выходном образе `kmod`.
- `update-pciids` требует доступного в целевой ОС
  загрузчика HTTP(S) и прав на обновление базы.
- `pcilmr` и `setpci` требуют соответствующего доступа
  к оборудованию; для диагностики доступен `lspci`.

## Альтернативы
- Хранить несжатую базу: не выбрано, поскольку zlib обеспечивает
  поддержку штатного сжатого формата.
