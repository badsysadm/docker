# Правила сборки `nell`

## Общие правила

- Архитектура: `x86_64`.
- Все зависимости линкуются статически, кроме `libc`.
- Тесты отключаются и не запускаются.
- Документация не собирается либо удаляется из конечного образа.
- Debian packaging используется как референс для build-зависимостей и флагов сборки. Пути установки из Debian не копируются.
- Финальный образ строится `FROM scratch` и содержит только необходимые артефакты в `/target`.
- Нестандартные и принципиальные решения конкретного проекта фиксируются в `ADR.md`.

## Структура сборки

Каждый проект состоит из:

```text
nell/<section>/<project>/
├── 01_src.Dockerfile
├── 02_dep.Dockerfile
├── 03_bin.Dockerfile
├── ADR.md
└── debian/control
```

### `01_src.Dockerfile`

Получает исходники указанной версии из официального upstream и помещает их в `/src`.

Для архивов используется потоковая загрузка через `wget` с тремя попытками,
выводом ошибок в файл и показом ошибки при неудачной распаковке:

```dockerfile
ARG VERSION=1.0.0

RUN mkdir -p /src/project && \
    wget --tries=3 -nv -O- "https://example.org/project-${VERSION}.tar.gz" 2>/tmp/project-wget.err | \
    tar -xzf - -C /src/project --strip-components=1 || { cat /tmp/project-wget.err >&2; exit 1; }
```

Для исходников из Git (в том числе GitHub) используется `git clone` с
`-q --single-branch --branch --depth 1`, с явным указанием версии и каталога:

```dockerfile
ARG VERSION=1.0.0

RUN git clone -q --single-branch --branch "v${VERSION}" --depth 1 \
    https://github.com/owner/project.git /src/project
```

Префикс `v` в имени тега используется только если он принят у конкретного
upstream; в остальных случаях указывается `"${VERSION}"`.

### `02_dep.Dockerfile`

Устанавливает build-зависимости из `debian/control` через `mk-build-deps`.

Для библиотечных зависимостей приоритет имеют существующие профили `nell`:
библиотеки из них берутся из соответствующих `bin`-образов. Если профиля
библиотеки в `nell` нет, используется Debian build-зависимость.

### `debian/control` и учёт встроенных зависимостей

В `Static-Built-Using` явно перечисляются статически встроенные зависимости
в формате `source-package (= version)`: для Debian — по `debian/control`
и версиям пакетов Debian, для собственных OCI-образов — по профилям `nell`.

### `03_bin.Dockerfile`

Компилирует проект и устанавливает результат в `/src/target`.

Если проект предоставляет библиотеки, на этапе `03_bin.Dockerfile` необходимо
собрать и установить **оба варианта библиотек: статические (`.a`) и
динамические (`.so`)**. Наличие только одного варианта не соответствует
правилам сборки `nell`.

**Все библиотеки (`.a` и `.so`) обязательно собирать с position-independent code (`-fPIC`).**
Статические архивы должны быть пригодны для включения в разделяемые библиотеки;
наличия PIC только у объектов, используемых для `.so`, недостаточно.
Для сборок на GCC обычно задаётся `CFLAGS="-O2 -fPIC"` (для C++ также
`CXXFLAGS`), с проверкой, что флаг применяется и к объектам статических архивов.

При линковке сторонние библиотеки переключаются в static mode, а `libc` остаётся динамической, например:

```text
-Wl,-Bstatic -lcrypto -lz -lzstd -Wl,-Bdynamic
```

После установки из `/src/target` удаляются документация и прочие ненужные runtime-файлы.

Финальный stage:

```dockerfile
FROM scratch AS bundle
COPY --from=build /src/target/ /target/
```

## Добавление проекта в Makefile

Проект необходимо добавить в соответствующую `section`:

```make
gnupg openssl krb5: section = security
```

и задать версию:

```make
krb5: version ?= 1.22.2
```

Имя target должно совпадать с каталогом:

```text
krb5 -> nell/security/krb5/
```

После этого проект должен собираться командой:

```bash
make krb5
```

## Проверка сборки

Перед признанием сборки готовой проверить:

- проект собирается через `make <project>`;
- тесты не собираются/не запускаются;
- документация отсутствует в `/target`;
- сторонние зависимости залинкованы статически;
- `libc` остаётся динамической;
- в `/target` нет build-файлов и других лишних артефактов;
- две последовательные сборки дают одинаковые SHA-256.
