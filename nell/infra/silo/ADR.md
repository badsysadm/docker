# ADR: профиль сборки Silo

## Статус
Принято для проверки сборкой.

## Решение
- Собирать PGSTY Silo из upstream Git-тега релиза, не использовать бинарники MinIO.
- Сохранять совместимость с существующим хранилищем MinIO как требование к выбору форка; сборка сама по себе не подтверждает совместимость данных.
- Использовать Go версии из upstream `go.mod` и `CGO_ENABLED=0`, как в официальной сборке Silo.
- Устанавливать build-зависимости через `debian/control` и выполнять `go mod vendor` в `02_dep.Dockerfile`.
- Собирать сервер `silo` в `03_bin.Dockerfile` без сети, с `-mod=vendor`, `-buildvcs=false`, `-trimpath` и upstream build tag `kqueue`.
- Фиксировать версию релиза, дату релиза и Git commit в штатных переменных `cmd`; не встраивать текущее время сборки.
- Не собирать и не запускать тесты; не включать документацию и инструменты разработки.
- Устанавливать серверный бинарник в `/target/usr/sbin/silo`; финальный образ — `FROM scratch`.
- Не включать `silo.service` и клиент `mcli` в профиль сборки: их доставка и настройка относятся к отдельной задаче эксплуатации.

## Последствия
- Silo сохраняет API и дисковый формат MinIO по заявлениям upstream, но переход с `RELEASE.2025-01-20T14-49-07Z` необходимо сначала проверить на копии томов вместе с `.minio.sys`, не открывая рабочие диски.
- Для запуска в systemd-portable нужен отдельный этап упаковки образа и конфигурации unit-файла.
- Сборка проходит штатной командой `make silo`; две последовательные сборки должны выдавать одинаковые SHA-256.
