# ADR: профиль сборки zot

## Статус
Принято для проверки сборкой.

## Решение
- Получать исходники zot из официального upstream Git-тега выбранной версии.
- Собирать полнофункциональный сервер `zot` с набором штатных расширений, включая встроенный Web UI, и клиент `zli`.
- Подготавливать Go и Node.js toolchain, Go vendor и npm-зависимости ZUI в `02_dep.Dockerfile`.
- Версию Go выбирать согласно требованиям `go.mod`, а ревизию исходников ZUI — согласно Makefile соответствующего upstream-релиза.
- Клонировать официальные исходники ZUI в `01_src.Dockerfile` и собирать их в `03_bin.Dockerfile` до компиляции Go, встраивая ресурсы в сервер с помощью `go:embed`.
- На этапе `03_bin.Dockerfile` компилировать без обращения к внешним репозиториям с `-mod=vendor`, `-buildvcs=false`, `-trimpath` и единым набором Go build tags для сервера и клиента.
- Использовать `CGO_ENABLED=0` и `GOEXPERIMENT=jsonv2`, как в upstream-сборке; не линковать динамические сторонние библиотеки.
- Не собирать и не запускать тесты; не собирать документацию и не включать её в конечный образ.
- Устанавливать только исполняемые файлы в `/target/usr/bin` с правами `0755`; финальный образ — `FROM scratch`.

## Последствия
- Функциональные расширения увеличивают время компиляции и число Go-зависимостей.
- Для обновления релиза может потребоваться согласованное изменение Go, Node.js и ревизии ZUI.
- ZUI компилируется из исходников вместе с сервером; воспроизводимость собранных ресурсов входит в общую проверку бинарников.
- Воспроизводимость итогового `bin`-образа проверяется штатной командой `make zot`.
