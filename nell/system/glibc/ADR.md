# ADR: разделение glibc на пакеты NELL и управление библиотечными зависимостями

## Статус
Принято.

## Контекст
glibc предоставляет динамический загрузчик, базовую библиотеку C и
дополнительные runtime-компоненты NELL. Их раздельная поставка позволяет
устанавливать необходимые компоненты независимо. Стандартное определение
Debian-зависимостей по ELF и shlibs/symbols-метаданным не гарантирует
соответствия собственному разбиению glibc на пакеты NELL.

## Решение
- Разделять glibc на базовые библиотеки, инструменты, средства разработки,
  необязательные компоненты и метапакет полного runtime; динамический
  загрузчик поставлять вместе с базовой libc.
- Использовать upstream-размещение относительно префикса `/usr` и staging
  root, сохраняя собственные библиотечные каталоги NELL вместо путей
  Debian multiarch.
- Поставлять скомпилированные локали отдельными пакетами, независимо от
  исходных данных для генерации локалей.
- Не использовать `${shlibs:Depends}` и не запускать `dh_makeshlibs` и
  `dh_shlibdeps` при упаковке glibc. Явно определять межпакетные
  зависимости по составу библиотек, ELF-зависимостям и назначению пакетов,
  чтобы автоматические метаданные не подменяли пакеты NELL системными.

## Последствия
- Можно устанавливать отдельные компоненты и готовые локали без полного
  набора инструментов и необязательных библиотек.
- Зависимости и принадлежность библиотек необходимо поддерживать вручную
  при изменении состава или ELF-зависимостей.
- Автоматические shlibs-метаданные для потребителей glibc не создаются:
  разрешение их зависимостей требует отдельной схемы учёта.

## Рассмотренные альтернативы
- Использовать стандартную генерацию shlibs-метаданных и автоматическое
  вычисление `${shlibs:Depends}` — отклонено, поскольку без отдельного
  описания нестандартного разбиения оно не обеспечивает соответствие
  зависимостей собственным пакетам NELL.
